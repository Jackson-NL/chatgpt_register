# 成功后二次风控缓解记录

> 日期：2026-08-16
> 目标：降低账号注册成功后一段时间内被二次风控/标记异常的概率，并保留可观测实验开关。

## 当前根因假设

基于代码链路取证，注册成功后原实现会立即执行一组高敏动作：

1. 新账号刚进入 `chatgpt.com` 首页后立刻抓取 Bearer `access_token`。
2. 立即调用 `/backend-api/accounts/mfa/enroll`。
3. 立即调用 `/backend-api/accounts/mfa/user/activate_enrollment`。
4. 立即调用 `/backend-api/accounts/mfa_info` 校验。
5. 后端账号入库后可立即触发健康检查 `/backend-api/me`。

这些动作都发生在新账号创建后的极短时间窗口内，容易形成“新号 + 临时邮箱 + 代理出口 + 立刻改安全设置 + 立刻 API 探测”的组合特征。

## 已落地缓解

### 1. 新账号冷却期

新增配置：

```env
NEW_ACCOUNT_COOLDOWN_MINUTES=120
```

注册成功后账号状态写为 `cooling`，并设置 `accounts.warmup_until`。冷却期内：

- 健康检查 `credential` 不再请求 `https://chatgpt.com/backend-api/me`；
- 检查结果返回 `warn`，detail 显示剩余冷却时间；
- 账号状态保持 `cooling`，不会被误标为 `unhealthy`。

### 2. 即时 TOTP 绑定开关

新增配置：

```env
REGISTRATION_BIND_TOTP=false
```

默认关闭即时 TOTP 绑定，用于降低成功后高敏动作密度。若需要恢复原行为，改为：

```env
REGISTRATION_BIND_TOTP=true
```

> 建议先用 false 跑一批样本，对比 2 小时/12 小时/24 小时存活率，再决定是否延后做 2FA 绑定任务。

### 3. 日志脱敏

实时日志现在会脱敏：

- JWT / access token
- TOTP secret
- 6 位 OTP/TOTP 验证码

避免前端日志、DB `logs_json`、控制台输出泄露敏感凭据。

## 推荐下一轮实验

1. A 组：`REGISTRATION_BIND_TOTP=false`，冷却 120 分钟，不做健康检查。
2. B 组：`REGISTRATION_BIND_TOTP=true`，冷却 120 分钟。
3. 对比指标：
   - 注册成功后 2h 是否仍可登录；
   - 12h 后 `/backend-api/me` 是否 200；
   - 24h 后是否触发 additional verification / disabled / suspicious。
4. 若 A 组显著优于 B 组，下一步应实现“延迟 2FA 绑定队列”，冷却结束后用同代理/同 profile 做低频绑定。
